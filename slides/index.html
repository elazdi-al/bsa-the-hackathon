Fuse · Wallet protocol · 01

Wallet signing and recovery

The wallet must remain recoverable when the phone is lost.

A smart account holds the assets and checks signatures.

Shamir shares help reconstruct its signing key.

Separate user credentials authorize payments and recovery.

The smart account is a contract, with an address that stays the same when its signer and passkey change. The Wallet Key is a signing key, not the account itself. We explain the design choices and then the setup and recovery steps. This is a prototype, with mocked bank identity verification.

Fuse · Wallet protocol · 02

Split the Wallet Key into three shares

APhone
BSwissquote
CIndependent service

Any two shares reconstruct the key. One alone cannot.

Normal signing uses A + B. A lost phone can be recovered using B + C.

The full key is reconstructed on the phone before signing.

Shamir uses a degree-one polynomial over the secp256k1 scalar field. Its value at zero is the Wallet Key. The shares occupy positions one, two, and three. Any two valid distinct shares reconstruct it. Feldman commitments let holders verify that a share belongs to the split. This is reconstruction followed by ECDSA signing, not distributed threshold ECDSA.

Fuse · Wallet protocol · 03

The two servers can also reconstruct it

B+C

Swissquote and the independent service hold a valid pair.

If they collude, they can produce a Wallet Key signature.

The key alone must not authorize a payment.

Shamir enables lost-phone recovery but does not prevent B+C collusion. The contract needs a separate user-controlled approval. The next slide explains the normal payment path and how the passkey supplies it.

Fuse · Wallet protocol · 04

Every payment requires the passkey

Swissquote sponsors gas and submits the signed operation. A cached Wallet Key still needs fresh passkey approval.

Normal mode checks the Wallet Key ECDSA signature and a WebAuthn assertion from the registered passkey over the same UserOperation hash. The phone verifies the operation before signing. On a cache miss, Swissquote verifies the assertion before releasing B. The key can remain in memory for at most three hours. The backend submits through EntryPoint v0.7 using a paymaster for sponsorship; there is no separate external bundler. B+C alone cannot satisfy the passkey check.

Fuse · Wallet protocol · 05

Recovery cannot require the lost passkey

The old phone and its passkey may both be unavailable.

The two servers must not be able to choose new credentials alone.

Someone asking for recovery must prove authorization.

Recovery needs a separate user-held secret.

Allowing B+C alone to replace the signer and passkey would bypass the payment protection. An impostor requesting recovery presents the same authorization problem. We cannot require the old passkey in the lost-device case, so we introduce a separate Recovery Key.

Fuse · Wallet protocol · 06

The Recovery Key authorizes recovery

A separate secret, created during setup and saved offline.

It is an authorization key, not another Shamir share.

It signs the exact new signer and passkey.

The account also requires a signature from the old Wallet Key.

Recovery authorization can only start credential replacement. It cannot make a payment.

The Recovery Key is independent of Share C. Its public address is registered with the account and share holders; the private key stays with the user, normally saved away from the phone. A Wallet Key signature binds the Recovery Key to the shares. Both services verify recovery authorization, and the account verifies the two signatures. Identity verification is mocked in this build, so the secret signature is an essential part of the demonstrated protection.

Fuse · Wallet protocol · 07

Set up the wallet once

Create a separate Recovery Key and save it offline. The Wallet Key signs its binding; register its public address.

The services verify shares against commitments. The partner URL is pinned in the app build so Swissquote cannot redirect C to itself. The Wallet Key signs the Recovery Key binding, checked by both holders. The account records the signer, passkey, Recovery Key, and Swissquote guardian. Share A is encrypted with WebAuthn PRF when available; this prototype falls back to unsealed storage without PRF. The factory predicts the account address before its first on-chain operation.

Fuse · Wallet protocol · 08

Start recovery on a new phone

First create the new passkey, Wallet Key, and shares. Only the new phone combines old B and C in this recovery flow.

The replacement key is bound to the existing Recovery Key. Swissquote prepares the recovery operation naming the new signer and passkey. After checking the Recovery Key signature, it releases old B and a five-minute signed approval ticket. The independent service checks the ticket, operation hash, recovery-only call, and bound Recovery Key signature before releasing old C. The new phone reconstructs the old key once to sign initiateRecovery. The account records the replacement credentials and the deadline. The old key from recovery is not added to the normal signing cache.

Fuse · Wallet protocol · 09

The Recovery Key can be stolen

Someone with that secret could request recovery as the user.

They still need the assisted B + C recovery process.

Immediate credential replacement would leave no time to respond.

Recovery therefore includes a cancellation window.

Possession of the secret can authorize an assisted recovery attempt when the services are available. The Recovery Key alone cannot directly spend funds, because the old Wallet Key signature and service assistance are still needed. The waiting period provides a chance to detect and cancel fraudulent recovery, not a guarantee of prevention.

Fuse · Wallet protocol · 10

Wait 48 hours before replacement

48hours, enforced on-chain

Cancel from the old phone, if available.

Or ask Swissquote to cancel as guardian.

If cancelled, the current credentials remain unchanged.

Old credentials remain active until finalization. The waiting period does not freeze spending.

The contract sets its deadline to block.timestamp plus 48 hours. Changing the browser clock does not shorten it. The old phone cancels using normal authorization. Swissquote can cancel directly as guardian; its app endpoint requires a Recovery Key-signed request. A second recovery initiation is rejected while one is pending. Cancellation remains possible after the deadline if finalization has not happened. Effective detection and notification are needed in production; production alerts are not implemented.

Anyone can call finalization after the deadline, but only the recorded replacement is installed. The new phone uses its new A and Swissquote's new B for normal signing. The same account continues to hold the assets; ordinary transactions during the wait can still change its balances. Both services must remain available for the implemented recovery flow. Losing the Recovery Key as well removes this recovery authorization path.
